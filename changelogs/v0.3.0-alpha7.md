# RxOn v0.3.0-alpha7 Release Notes - "Refined Configuration & Diagnostics"

This release focuses on improving the library's initialization experience and ensuring diagnostic consistency by refining the `RxOnConfig` builder and the error mapping pipeline.

## New Features & Refinements

### 1. Non-Exclusive Configuration DSL
The `RxOnConfig.builder()` has been updated to remove the mutual exclusivity between stacktrace cleaning and error mapping. You can now configure both in a single fluent chain:

```java
RxOnConfig.builder()
    .debug(true)
    .logger(myLogger)
    .cleanStackTrace(true) // Now available before errorMapper
    .errorMapper(myMapper) // Can be called after cleanStackTrace
    .init();
```

### 2. Logical Builder Step Order
The builder DSL now offers the `cleanStackTrace` step before the `errorMapper` step. This better reflects the internal execution flow and encourages developers to decide on diagnostic noise reduction before defining custom mapping logic.

### 3. Improved Error Mapping Pipeline
`RxOnConfig.mapError` now applies stacktrace cleaning **before** the custom `RxOnErrorMapper` is invoked. 
- **Benefit**: Custom error mappers now receive a "clean" exception. This makes it significantly easier to perform pattern matching on causes or log meaningful stacktraces without the overhead of RxJava internal frames or library wrappers.

## Breaking Changes
- **Builder Interface Change**: If you were previously implementing the `RxOnConfig.ErrorMapperStep` interface manually, you will need to update your implementation to match the new step chain (the introduction of `StackTraceStep`). However, most users using the fluent API will not be impacted, though the method order in the chain has changed.

## Bug Fixes
- Fixed an issue where `cleanStackTrace` and `errorMapper` could not be used together during initialization.
- Fixed the execution order in `mapError` where stacktrace cleaning was erroneously applied after error mapping, potentially obfuscating details needed by the mapper.
